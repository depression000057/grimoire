# 品質工程

- 役割: 書いた文を、そのまま出さずに仕上げる順番を決める。どのモードで書いた文も、この順を通してから提出する
- いつ読むか: Threads 投稿・note・ローンチの告知文など、読者に向けた文を書き終えた時
- 目次: §1 なぜ工程を分けるのか §2 全体の順番 §3 各段の中身 §4 Threads の場合 §5 note の場合 §6 別のAIに任せられる環境 §7 省いてよい時・省いてはいけない時

## §1 なぜ工程を分けるのか

書いた本人（AI も同じ）は、自分の文の「言いたいこと」を知っているので、読者が迷う所に気づけない。また、きちんと書こうとするほど、文は硬く、説明っぽくなる。そこで、書く・壊れを探す・話し言葉に直す・意味がずれていないか確かめる、を別の段に分け、段ごとに違う目で読む。

もう1つの理由: 話し言葉に直すと、読みやすくなる代わりに、元の主張や数字や約束の強さが少しずつ変わることがある。直した後に、直す前と並べて意味を確かめる段を必ず置く。

## §2 全体の順番

| 段 | やること | 手順書 |
|---|---|---|
| 1 | 設定・カード・お手本を読む | 各モードの「読むもの」 |
| 2 | 通しで1回書く（元稿） | 各モード |
| 3 | 日本語の破綻を点検して直す | `references/quality/breakdown-checklist.md` |
| 4 | 書き直し担当に切り替え、話し言葉に書き直す（書き直し稿） | `references/quality/rewrite-pass.md` |
| 5 | 元稿と書き直し稿を並べ、意味のすり替わりを探す | `references/quality/meaning-check.md` |
| 6 | 書き直し稿を土台に、意味が変わった所だけ元稿の言葉に戻す（統合稿） | §3 |
| 6b | 事実と声の照合（本人について書いた事実と、本人の声を、設定・実績と1つずつ照らす） | §3 |
| 7 | 機械チェック | `scripts/tn_check.py`／各モードのチェックリスト |
| 8 | 読者目線で頭から読む | §3 |
| 9 | 提出 | `SKILL.md`「提出の形」 |

## §3 各段の中身

**段2 通しで書く**: 途中で推敲しない。最後まで書き切ってから段3に進む（途中で直し始めると、全体の流れより目の前の1文を整えることに気を取られるため）。

**段3 破綻の点検**: 全文を1文ずつ、`breakdown-checklist.md` の問いに当てる。落ちた文は、言い換えで救わずに、その文を消して別の文を作る（言い換えだけだと、壊れた骨組みが残るため）。主語と、指す言葉（これ・それ）が何を指すかの抜けは、段4では直らないので、ここで必ず直す。

**段4 書き直し**: 書き手の自分から離れ、「書き直し担当」になって `rewrite-pass.md` の手順で書き直す。字数は元稿の±5%以内。言い直しや例を足さない。

この段は省かない。「下書きの時点で話し言葉だったから、書き直す所は無い」と判断して飛ばすのが、一番起きやすい失敗（書いた本人の目には、自分の文はいつも自然に見えるため）。飛ばさないために、書き直し担当は `rewrite-pass.md` §6 の診断の観点ごとに「該当する文（引用）／該当なし」を1行ずつ書き出してから書き直す。書き出した記録は、制作物のファイルとは別に `ティルナノーグ_制作物/_作業中/` に置き、提出の時に「書き直しで直した所: N か所」と1行で報告する。直す所が本当に0か所だった時も、観点ごとの「該当なし」の記録は残す。

**段5 意味の点検**: `meaning-check.md` の表で、主張・事実と数字・読者にしてほしい行動・因果・約束の強さ・対象の読者・否定と条件、の7つを元稿と書き直し稿で比べる。

**段6 統合**: 必ず**書き直し稿を土台**にする。

1. 書き直し稿をまるごと写す
2. 段5で「意味が変わった」とした所だけを、元稿の言葉・数字・固有名に戻す
3. 戻す時に、強い約束や言い切り（キラーワード）を弱める方向には戻さない

逆の順番（元稿を土台にして、書き直し稿の良い所をつまむ）はしない。元稿の硬さが残り、書き直しの効果がほとんど消えるため。

**段6b 事実と声の照合**: 統合稿の中から、次の2種類を全部抜き出し、1つずつ照らす。

1. **本人について書いた事実**: 期間（何年も・ずっと）、回数（毎日・何度も）、数字（分・円・人数）、結果（〜になりました・なくなりました）、読者の反応（よく届く・多くの人から・「〜という声をもらう」「よく聞かれる」）、経験・資格、**本人のやり方（手順・分量・レシピ・道具・コツ・「〜がちょうど良かった」という経験の結論）**、健康・安全・お金に関わる一般情報（保存期間・効果・金額など）
   - `00_わたしの設定.md`・`10_お手本/`・`40_実績/`・制作物のフォルダの `中身の素材_本人の答え.md`・今の会話で受講生が言ったことの、どこかに裏付けがあるか
   - 裏付けが無いものは、次の順で扱う
     1. 本人の事実より強い言い方（盛り）: 裏付けのある言い方に戻す（「20分で終わる」を「0分になった」にしない）
     2. 健康・食品の安全・お金・法律に関わる手順: 下の「読者が真似する手順」の項目のとおり、一次情報に置き換えるか消す。本人の返事を待たずに直す
     3. 本人に聞けば分かるもの: 枠（`<!-- ここに〜 -->`）にするか消して、「確かめてほしいこと」で聞く。ただし、前の記録（点検記録など）に「本人が答えた」と残っているのに、答えのファイルが見つからない時は、本文を残したまま「確かめてほしいこと」の1番目で聞く（消すと、本人が実際に答えた中身まで失うため）
   - 本人がやっていない工夫・助言（例: 本人が言っていない調理のコツ）を、本人の経験のように書かない
   - note の有料本編では、やり方の文を全部抜き出して、`references/modes/2_note.md` §3 の中身の素材の表と1つずつ照らす。表に無いやり方は、枠（`<!-- ここに〜 -->`）にするか、「一般的には〜」と本人の経験から切り離して書く
   - 実在しない読者の声・よくある質問（「〜という声をもらいます」「よく聞かれます」）を作らない。本人から受け取った声だけを使う
   - 読者が真似する手順のうち、健康・食品の安全・お金・法律に関わるもの（保存期間・解凍・加熱など）は、公的機関などの一次情報と1つずつ照らし、照らした確かめ先を記録に残す。本人の確認は安全の裏付けにならない。一次情報と違う・確かめられない手順は、読者に勧める形で残さない（`absolute-rules.md` の決まり5と §4）。一次情報のやり方に置き換えた時は、本人がそのやり方をしているとは書かず、本人の実際のやり方と違っていたことを「確かめてほしいこと」で本人に伝える。本人の習慣（「2週間以内に使い切る」など）は、読者への目安ではなく本人の習慣として書く
   - 設定で「仮」と印が付いている項目は、本文の事実としては使わない。使いたい時は「確かめてほしいこと」に回し、本人の返事を待つ（「仮」は推定なので、本人の経験として書くと盛りになるため）
2. **本人の声**: 設定の「声」の節（一人称・語尾・改行の癖・絵文字・締め方）と、1項目ずつ照らす。特に改行の癖（「1文ごとに改行」など）は、書き直しの段で崩れやすいので、最後にここで直す。改行の癖は媒体ごとに違うことがある。note を書く時は「note の改行」の行を使い、その行が空なら、Threads の癖を note にそのまま当てはめず、段落で書いたうえで「note も1文ごとに改行しますか」を確かめてほしいことに回す（答えは設定の「note の改行」に書き足す）

このあとの段7の機械チェックも、盛りやすい言葉（何年も・一番・0分 など）と声のずれを「目視候補」として出す（Python が動く環境のみ）。候補が出たら、この段の照合に戻る。

照合で直した所は、提出の時に「事実と声の照合で直した所: N か所」と1行で報告する。盛りを1か所でも残すと、受講生の信用を傷つけるため（`references/quality/absolute-rules.md` の決まり2）。

**段7 機械チェック**: チェックは、保存した制作物のファイルそのものに当てる。案を比べるために一時ファイルを作った時は、`ティルナノーグ_制作物/_作業中/` に置き、そのまま残してよい（消す操作は、受講生の画面に確認が出るのでしない）。違反（直す）と目視候補（人が判断）が出る。違反は文ごと直す。目視候補は、読んで自然ならそのまま残してよい（機械の言うとおりに語だけ差し替えると、かえって不自然になるため）。

ただし、目視候補のうち **声のずれ（VOICE_…）と、本人の事実か確かめる語（VERIFY_FACT）** は、1件ずつ「直した」か「理由があって残した（理由1行）」を決めて記録する。放置しない（この2種類は段6bの照合の取りこぼしを拾うためのもので、残すと本人らしさと信用に直接響くため）。

チェックは、配布されたスキルのフォルダの `scripts/tn_check.py` を、必ず `--settings <マイナレッジ>/00_わたしの設定.md` を付けて、提出するファイルそのものに当てる。最後に当てた時の結果（違反の数・目視候補の数・声と事実の候補をどう処理したか）を提出メモに書く。違反が0件になる前に、貼り付け用の書き出し（`tn_paste.py`）をしない。

**段8 読者目線**: 設定の「読者1人」になったつもりで、頭から声に出すつもりで読む。次のどれかが起きた所を直す。

- 読むのをやめたくなった
- 前に戻って読み直した
- 「それって何？」と思った言葉があった
- 「で、私は何をすればいい？」と思った

## §4 Threads の場合

1本が短いので、段3〜段6を1本ずつ続けて行ってよい。10本以上の時は、段4の書き直しを5本ずつまとめて行う（1本ずつだと声がばらつき、全部まとめると後半が雑になるため）。段8は、1本ずつ「スクロールを止めるか」「最後まで読むか」を聞く。

## §5 note の場合

全段を通す。note は長いので、段3と段4は章ごとに行ってよい。段5の意味の点検は、章ごとの表を作る。段8だけは全文を通しで読む（章をまたぐ気持ちの流れは、通しでしか確かめられないため）。

**中身が固まった後に、言い方の仕上げをもう1周する**: 段8や受講生の確認で中身（数字・順番・章の並び・効果の言い方）を直すと、直した文や書き足した文は段4の書き直しを通っていない。中身を固める作業と言い方を磨く作業は別なので、中身が固まった後に、直した章だけ段3〜段6をもう1周通す。止め方は次のとおり（無限に回さない）。

- 周の終わりに、`breakdown-checklist.md` と `rewrite-pass.md` の観点で1文ずつ見直し、直す所が0になったら止める
- 最大4周。4周しても直す所が残る時は、残った文と理由を「確かめてほしいこと」に書いて提出する（「完成」とは言わない）
- 同じ文が2周続けて直す所に残ったら、3周目はその文を言い換えず、前後1〜2文ごと書き直す（1語ずつ言い換えても、同じ所でつまずくため）
- 直す提案が、効果を強める・数字を足す・設定の禁止語を使う方向なら採らない
- 周を回した後に1文でも直したら、その文のためにもう1周回す

## §6 別のAIに任せられる環境

- 別の AI に頼めない環境（1つの AI が1回の返事で全部行う環境）では、段4の前に「ここから書き直し担当。これまでの設計の話は使わない」と自分に宣言し、元稿だけを見て書き直す。段4の診断の記録（観点ごとの該当・該当なし）を必ず残す。記録が無い書き直しは、行っていないのと同じに扱う
- 手伝いのAI（サブエージェント）を呼べる環境では、段4の書き直しと段8の読者目線を、元稿を書いたのとは別のAIに頼む。頼む時は、元稿と `rewrite-pass.md`（段4）、または本文だけ（段8）を渡す。設定や意図の説明は渡さない（読者と同じ条件で読ませるため）

## §7 省いてよい時・省いてはいけない時

- 省いてよい: 受講生が「下書きだけ」「ざっと」と言った時は、段4〜段6を省いて、提出時に「仕上げ前の下書きです」と書く
- 省いてはいけない: 段3（破綻の点検）・段6b（事実と声の照合）・段7（機械チェック）と絶対ルールの確認は、どんな時も省かない
- 2案以上から選んでもらう時: 全部の案に段3と段7までを通して出し、「選ばれた案に書き直しと意味の点検をかけて仕上げます」と添える。選ばれたら、その案だけに段4〜段8を行って最終稿を出す（選ばれない案まで仕上げると、受講生を待たせるだけになるため）
